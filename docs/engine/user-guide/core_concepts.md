# 游戏开发必读：核心概念

本文介绍使用 Elysia Engine 开发游戏前需要理解的基本概念：场景与对象、所有权与生命周期、更新机制、对象状态和坐标系统。最后用生命药水串起这些概念；案例展示职责与步骤，不是可直接运行的完整游戏。

> **阅读说明**：本文着重解释游戏层应遵守的行为约定，而非引擎内部的全部实现。

## 2. 场景、游戏对象与 UI 各负责什么

核心关系可以简化为：

```text
Scene（组织运行内容，持有对象）
└── SceneObject（对象公共基类）
    ├── GameObject（游戏世界对象）
    └── UiElement（UI 元素）
```

这里表示的是**组织与继承关系的组合示意**：`Scene` 持有对象，不继承 `SceneObject`；`GameObject` 与 `UiElement` 则继承自 `SceneObject`。

### 2.1 SceneObject：公共基类

`SceneObject` 为场景对象提供活跃、可见、销毁等基本状态，以及重置和暂停行为相关接口。绘制指令提交接口分别由 `GameObject` 和 `UiElement` 提供。以下仅列方法名，省略参数与声明：

```cpp
// GameObject：提交世界对象绘制指令。
submit_render_commands(...);
// UiElement：提交 UI 绘制指令。
submit_ui_render_commands(...);
```

需要绘制的对象负责组装自己的绘制指令，再由场景系统收集并统一执行。**提交指令不等于立即绘制**；对象也不一定要提交任何绘制内容。

继承 `SceneObject` 不意味着自动获得逐帧更新、输入响应或物理碰撞能力。这些功能需要根据对应系统的规则显式实现和接入。

### 2.2 Scene：运行内容的组织者

`Scene` 用来组织一段独立的运行内容，例如：

```text
MainMenuScene
SpecialEventsScene
BattleScene
```

它持有场景对象，协调输入、更新、绘制指令收集以及对象清理，并管理场景进入、退出和重置流程。场景适合负责**对象组织与整体流程**，不必承包每个对象的具体行为。

例如，一个 `BattleScene` 可以组织玩家、敌人、道具、背景及战斗 UI。玩家移动应由玩家或控制相关逻辑负责，道具拾取由道具或交互系统负责，而不是把所有行为都塞进 `BattleScene`。

每个场景拥有自己独立的对象集合。从所有权角度，可以概念性地理解为：

```cpp
std::vector<std::unique_ptr<elysia::core::SceneObject>> objects;
```

这只是所有权示意，省略了世界对象与 UI 根节点的分类存储，不代表真实容器布局。场景只接受 `GameObject` 或 `UiElement` 派生对象，不能直接添加任意 `SceneObject` 派生类。



### 2.3 GameObject：游戏世界对象

`GameObject` 表示世界中的角色、道具、弹丸或装饰等对象。它提供世界矩形、绘制层级和层级内顺序等基础能力。

但继承 `GameObject` **不会自动获得**：

- 移动或输入响应；
- 物理刚体、碰撞器或拾取检测；
- 逐帧更新与固定步更新。

这些能力需要按实际需求实现，并接入对应的更新或子系统。静态装饰和玩家角色虽然都可能是 `GameObject`，但不必拥有相同的行为。

### 2.4 绘制层级与遮挡顺序

创建 `GameObject` 时，需要通过构造函数指定 `DepthLayer`，并可通过参数 `order` 指定层内顺序（默认为 `0`，用 `order_in_layer()` 查询）。这两项决定世界对象的绘制先后。

当前层级按以下顺序从后向前绘制：

```text
Background → Terrain → EffectBack → Item → Character → EffectFront → Foreground
```

后绘制的内容通常显示在先绘制的内容之上，实际遮挡还取决于透明度等绘制设置。`Count` 只是枚举中的层数标记，不是可用的绘制层级。

层级名称用于表达对象的绘制用途，例如背景使用 `Background`，道具使用 `Item`，角色前方的特效使用 `EffectFront`。它们不会自动赋予对象行为：选择 `Character` 不会获得角色能力，选择 `Terrain` 也不会自动产生碰撞。

**先比较层级，再比较层内顺序。** 同一层中，`order_in_layer()` 越大，绘制越晚；它不能跨越层级。即使 `Item` 层对象的层内顺序很大，`Character` 层仍在它之后绘制。

例如，药水可以在自己的构造函数中选择道具层：

```cpp
HealthPotion()
    : GameObject(elysia::core::DepthLayer::Item, 0)
{
}
```

UI 使用独立的排序体系。当前场景先绘制世界对象，再绘制 UI；提高 `GameObject` 的绘制层级或层内顺序，不能让它覆盖 UI。

### 2.5 UiElement：界面元素

`UiElement` 表示按钮、HUD 血条、背包面板等界面元素，可以直接加入场景，也可以加入 UI 容器。加入容器的子节点由所属容器持有，并遵循该容器的布局、交互和清理流程。角色头顶随世界相机移动的名字和血条另见[世界空间 Gameplay UI](gameplay/world-ui.md)。

`UiElement` 和 `GameObject` 都继承 `SceneObject`，但**共享基类不代表共享坐标体系或更新机制**：

| 特性 | `GameObject` | `UiElement` |
| --- | --- | --- |
| 用途 | 世界中的角色、敌人、道具等 | 按钮、血条、背包等 |
| 坐标 | 世界坐标 | UI 坐标及容器布局 |
| 摄像机 | 绘制经过对应的世界摄像机投影变换 | 不跟随普通世界摄像机投影 |

例如，掉在地图上的 `HealthPotion` 是 `GameObject`；背包里展示药水的图标属于 UI。背包**数据**最好由独立的游戏逻辑维护，UI 负责展示，不应把即将销毁的世界道具指针直接当作背包数据。

## 3. 对象的创建、归属与所有权

所有对象**成功加入场景后，由场景持有**。UI 子节点若加入了容器，则由对应容器持有。不要让两个所有者同时管理同一个对象。

场景提供的对象创建与添加接口形式如下；这里省略模板声明和类型约束，不是可直接复制的完整声明：

```cpp
T* create_and_add_object(Args&&... args);
T* add_object(std::unique_ptr<T> object);
```

### 3.1 由场景创建对象

假设 `HealthPotion` 提供无参构造函数：

```cpp
HealthPotion* potion = scene.create_and_add_object<HealthPotion>();
```

使用 `create_and_add_object` 时，需要指定对象类型；括号中填写构造该对象所需的参数，接口会将参数完美转发给构造函数。具体参数取决于当前类的定义。

### 3.2 转移已创建对象的所有权

```cpp
auto potion = std::make_unique<HealthPotion>();
HealthPotion* raw = scene.add_object(std::move(potion));
```

`std::move()` 用于转移 `unique_ptr` 的所有权。对象成功加入后由场景管理；原来的 `unique_ptr` 不再拥有它。

创建或注册失败可能返回空指针，也可能抛出异常。调用后检查返回值；不能假定失败会把所有权交还原指针。同步添加只能在允许修改对象集合的阶段进行，具体位置见[场景阶段表](scene/scene.md#常用操作与扩展点)。

### 3.3 返回的裸指针不是所有权

两种接口都返回 `T*`，但这只是访问入口，不负责释放对象：

```cpp
HealthPotion* potion = scene.create_and_add_object<HealthPotion>();

// 错误：场景已经持有对象。
// delete potion;

// 错误：不能为同一对象重新制造第二个拥有者。
// std::unique_ptr<HealthPotion> another_owner(potion);
```

**场景管理对象的生命；返回的裸指针只提供访问能力。**

## 4. 对象的生命周期与销毁

### 4.1 `destroy()` 只是标记销毁

所有 `SceneObject` 的 `destroy()` 只标记对象需要销毁，不会在调用处立即释放内存：

```cpp
potion->destroy();
```

场景直接持有的对象，会在更新末尾（`on_after_update` 之后）、退出回调后或重置回调后的清理点移除并释放；UI 容器的子节点则由所属容器清理。

如果在 `on_exit()` 中标记场景对象销毁，它会在该次退出流程内回收，不必等待再次进入。未标记对象可以随缓存场景保留供 Reuse 使用；Reset 调用场景 `on_reset()`，不自动清空或重置所有业务对象。

标记后应将对象视为即将退出使用，不依赖它暂时还在内存中来安排新的业务操作。

### 4.2 裸指针不会自动变成空指针

```cpp
HealthPotion* potion = scene.create_and_add_object<HealthPotion>();
if (potion)
    potion->destroy();

// 随后执行场景清理时释放对象。
// 对象释放后，potion 不会自动变为 nullptr。
```

对象实际释放后，之前保存的 `potion` 可能成为**悬空指针（dangling pointer）**。仅检查非空不能证明对象仍然有效：

```cpp
if (potion != nullptr)
{
    // 不能据此认定对象仍然存活。
}
```

即使写成下面这样，也不能检测已经释放的对象：

```cpp
if (potion && !potion->is_destroyed())
{
    // 调用 is_destroyed() 本身就要求 potion 指向有效对象。
}
```

必须区分：

| 情况 | 含义 |
| --- | --- |
| `nullptr` | 指针为空 |
| 有效指针 | 指向仍然存活的对象 |
| 已标记销毁 | 对象可能尚未释放，但已进入销毁流程 |
| 悬空指针 | 对象已释放，旧指针可能仍然非空 |

### 4.3 延迟清理的时间线

```text
调用 potion->destroy()
        ↓
对象被标记为待销毁（不会在调用处立即 delete）
        ↓
实际执行场景清理点
        ↓
场景在更新末尾或退出／重置回调后：移除并释放待销毁对象
        ↓
外部保留的 potion 指针可能悬空
```

不要将延迟清理理解成对象存活到下次更新的绝对保证。

### 4.4 跨帧引用与回调

保存 `Player*`、`Enemy*`、`HealthPotion*` 等非拥有指针本身并非错误，但必须明确：

- 被引用对象何时可能销毁？
- 当前对象或回调是否可能比被引用对象存活更久？
- 场景切换、重置后，引用是否仍然有效？
- 谁负责在适当时机解除引用？

尤其不要让生命周期更长的事件回调捕获一个已经释放的对象指针。在没有专门的安全引用机制之前，开发者需要自行维护跨帧引用的有效性。

`std::unique_ptr` 解决**所有权**问题，并不会让其他裸指针自动失效或自动变成 `nullptr`。

## 5. 场景缓存、进入与重新进入

场景可能被缓存。退出场景不等于销毁场景实例，再次进入也不一定重新构造所有对象。因此，需要区分保留状态、重置状态与重建实例。

游戏场景需要实现以下三个扩展点。这里列出简化签名，`ScenePayload` 位于 `elysia::scene`：

```cpp
on_enter(const ScenePayload& payload);
on_exit();
on_reset();
```

`on_enter()` 与 `on_exit()` 分别对应进入和离开；Reset 路由由引擎先重置框架状态，再调用 `on_reset()` 恢复业务状态。游戏不直接调用这些生命周期函数。对象的 `reset()` 是另一个接口，场景不会自动替所有业务对象调用它。

场景重新进入模式定义为：

```cpp
enum class SceneReloadMode
{
    Reuse,
    Reset,
    Recreate
};
```

可以按设计意图理解为：

| 模式 | 含义 |
| --- | --- |
| `Reuse` | 复用已有场景 |
| `Reset` | 对已有场景执行重置流程 |
| `Recreate` | 重新创建场景实例 |

重新进入场景时，不要默认道具数量归零、敌人已清空、事件绑定已解除，或旧指针仍然有效。先确认当前场景的退出与重置逻辑，再决定哪些数据要保留或清理。

例如，从暂停菜单返回关卡可能需要保留状态；重新开始关卡则可能需要重新生成敌人、重置玩家位置和清空本局掉落物。两者不应混为一谈。

## 6. 代码什么时候执行

可以先用下面的**概念性流程**理解正常运行的一帧：

```text
输入处理
   ↓
场景更新
  ├─ 普通更新
  ├─ 根据时间累积按需执行固定步更新
  ├─ 执行引擎规定的其他流程
  └─ 更新末尾：清理待销毁对象
   ↓
渲染
```

以上仅为概念性流程，不代表引擎内部的完整调用顺序。

### 6.1 普通更新：`update`

普通游戏对象需要实现 `Updatable` 并加入场景，才会被登记到相应逐帧更新流程。只继承 `GameObject` 或只写一个同名方法，不意味着引擎自动调用它。能否在当前帧执行，还取决于对象状态和暂停规则。

普通更新中的 `delta` 是时间增量，单位为秒。假设速度是每秒 100 个世界单位，那么按帧写死移动量会造成帧率依赖：

```cpp
// 错误思路：每帧移动固定距离，实际速度随帧率变化。
position.x += 100.0f;

// 基本时间计算思路：按经过时间推进。
position.x += 100.0f * delta;
```

以上只是时间计算示例。如果对象由物理系统驱动，应遵守物理模块的状态修改规则，而不是擅自改写位置。

`update` 通常适合一般游戏行为、普通计时器、技能冷却、非物理驱动的动画状态，以及按帧间隔推进的表现逻辑。例如：

```cpp
// 私有成员：double _cooldown = 0.0; // 剩余冷却时间，单位为秒。
// 在 update(double delta) 中更新：
_cooldown = std::max(0.0, _cooldown - delta);
```

实际使用时，应确认 `delta` 遵循的游戏时间、暂停和时间缩放规则。

### 6.2 固定更新的扩展点

固定更新使用固定模拟时间步长。它不与渲染帧数一一对应：某一渲染帧可能执行零次、一次或多次固定更新。

固定更新通常适合：

- 物理模拟；
- 与固定步物理状态紧密耦合的行为；
- 需要稳定模拟步长或特定更新顺序的游戏规则。

普通 `Scene` 启用固定步后使用 `on_fixed_update(tick, delta)`；`GameplayScene` 使用 `on_game_fixed_update(tick, delta)`；注册到物理世界的 `PhysicsStepParticipant` 使用 `fixed_update(double)`。只给普通对象增加同名方法不会自动参与固定步。接入方式见[物理指南](systems/physics.md)。

不要在逐帧更新和固定步中分别推进同一份物理状态，避免重复移动或状态不同步。

简化的选择参考：

| 需求 | 通常使用 |
| --- | --- |
| 普通计时器与一般技能冷却 | `update` |
| 一般非物理驱动的表现状态 | `update` |
| 物理模拟 | 对应的固定步物理系统 |
| 与物理模拟同步的游戏规则 | 场景固定步钩子或 `PhysicsStepParticipant::fixed_update` |

### 6.3 渲染只负责呈现状态

世界对象的 `submit_render_commands(...)` 和 UI 的 `submit_ui_render_commands(...)` 负责组装绘制指令，不应顺便发放奖励、扣血、消费输入、推进计时或修改会影响游戏规则的状态。否则游戏逻辑会依赖渲染是否执行及渲染帧率。

基本原则：

```text
更新阶段：计算并修改游戏状态
渲染阶段：根据当前状态提交绘制指令
```

## 7. 容易混淆的对象状态与暂停

### 7.1 可见性

通过 `set_visible()` 修改、`is_visible()` 查询。可见性控制相应绘制流程，不等于停止更新、碰撞、计时或输入。隐藏一个道具，不会自动完成拾取，也不会自动销毁它。

### 7.2 活跃状态

通过 `set_active()` 修改、`is_active()` 查询。活跃状态用于筛选相应的更新和输入流程，不等于不可见。以普通 `GameObject` 为例，场景绘制检查可见和销毁等状态，不把活跃状态直接当作绘制开关。

### 7.3 销毁状态

通过 `destroy()` 标记、`is_destroyed()` 查询。销毁状态表示对象准备退出使用，和临时隐藏或停用不同。对象只是暂时不可见时，不一定需要销毁；一次性道具拾取完毕后则可以进入销毁流程。

### 7.4 暂停状态

暂停时，场景会跳过不允许在暂停期间更新的对象，并停止该场景的物理推进；允许暂停时工作的对象仍可运行。输入处理也有单独的暂停规则。

场景的 `on_before_update()` 和 `on_after_update()` 仍会被调用。在这两个钩子中推进需要随暂停停止的业务时，显式检查 `is_paused()`；全局时间也不会因场景暂停而停止。

暂停菜单仍需要响应按钮输入和播放 UI 动画。**不要推断场景暂停就意味着整个应用程序完全静止。**

## 8. 世界坐标、UI 坐标与渲染位置

### 8.1 不同坐标不能直接混用

世界坐标描述角色、敌人和道具在游戏世界中的位置。窗口坐标与逻辑渲染坐标需要区分：窗口缩放或逻辑画面映射后，它们不一定一一对应。引擎输入系统会将鼠标的窗口坐标转换为逻辑渲染坐标；`Camera::world_to_screen()` 返回相机视口中的逻辑渲染坐标，不能直接当作实际窗口像素。UI 位置还可能受所属容器的局部坐标和布局影响。

例如，鼠标位置如果是屏幕坐标，而药水矩形是世界坐标，不能直接进行拾取判定：

```cpp
// 如果 mouse_position 为屏幕坐标，potion_rect 为世界坐标，
// 则不能直接比较：
// potion_rect.contains(mouse_position);
```

应先通过对应的摄像机或坐标转换机制，把数据转换到**同一坐标空间**，再进行比较。

以下片段放在已启用相机的场景成员函数中；`object` 是仍有效的世界对象：

```cpp
// 对象逻辑中心对应的屏幕位置
const elysia::core::Vector2 screen_center = camera().world_to_screen(object.center());

// 对象显示矩形对应的屏幕区域
const elysia::core::Rect screen_rect = camera().world_to_screen(object.render_rect());
```

### 8.2 `world_rect()` 与 `render_rect()`

`world_rect()` 表示对象的世界矩形；`render_rect()` 可以包含物理插值带来的显示偏移。

对应插值机制正常工作时，显示偏移由引擎自动计算，**不需要**手动更新。

**游戏规则使用逻辑状态；绘制使用对应的呈现状态。** 不要把用于平滑显示的插值位置写回业务或物理状态。

## 9. 概念案例：局内掉落道具 `HealthPotion`

假设游戏需要实现：玩家看见地图上的生命药水，满足拾取条件后恢复生命值，药水从世界中消失；如有背包功能，也可以改为将物品存入背包。

下面的片段省略头文件、绘制资源、玩家类型和拾取检测，仅说明各部分如何分工。可编译的对象类型示例见[游戏对象与绘制](scene/game-objects.md)。

### 第一步：定义对象

```cpp
class HealthPotion : public elysia::core::GameObject
{
public:
    HealthPotion()
        : GameObject(elysia::core::DepthLayer::Item, 0)
    {
    }

    // 按需求实现绘制、拾取相关行为等。
};
```

它继承 `GameObject`，因为它是世界中的道具。但拾取碰撞器、输入交互或逐帧更新**不会因此自动存在**，必须按所选方案显式接入。静止且只等待交互的道具也不一定需要逐帧更新。

### 第二步：将对象加入场景

使用上面定义的无参构造函数：

```cpp
HealthPotion* potion =
    scene.create_and_add_object<HealthPotion>();
```

检查 `potion` 非空后，用 `set_world_rect()` 设置位置和尺寸，再按下一步实现绘制。场景须显式启用相机才能显示世界对象。成功加入后，场景持有该对象，返回指针只是访问入口。

### 第三步：按需实现绘制和交互

药水可以提交对应的绘制指令。拾取检测则由游戏层选择合适的实现方式，如触发区域、交互系统或对象查询。

如果道具需要上下漂浮、计时消失等行为，再按需求实现并登记对应更新能力。不需要为所有道具无条件启用每帧更新。

### 第四步：处理拾取

```text
确认玩家满足拾取条件
        ↓
恢复生命值，或更新背包数据
        ↓
避免同一药水重复发放效果
        ↓
标记药水销毁：potion->destroy()
```

拾取逻辑应防止同一对象被重复处理；效果发放后，将药水标记为待销毁，交给场景清理。

### 第五步：释放与引用清理

按第 4 节的生命周期规则，检查交互目标、选中对象和延迟回调中是否保存了药水引用，并在对象释放前解除不再有效的关联。

### 第六步：更新背包 UI（如有）

建议分离以下职责：

```text
HealthPotion     世界中的道具实例
Inventory        保存物品类型、数量等游戏数据
InventoryPanel   显示背包
InventorySlot    显示单个物品
```

拾取时先更新玩家库存数据，再标记世界中的药水销毁，由 UI 读取库存数据并更新显示。不要直接把世界对象的 `HealthPotion*` 当作长期背包记录，否则场景清理后容易留下悬空指针。

## 10. 常见误区速查

| 误区 | 正确认识 |
| --- | --- |
| 继承 `GameObject` 就会自动更新 | 必须实现并登记相应更新能力 |
| 继承 `GameObject` 就会自动碰撞 | 需要配置并接入物理或交互系统 |
| `destroy()` 立即释放对象 | 只是标记；场景对象在随后实际执行的清理点释放 |
| 裸指针非空表示对象有效 | 释放后可能成为非空的悬空指针 |
| 隐藏对象就停止所有行为 | 可见性主要控制对应绘制流程 |
| 对象不活跃就一定不可见 | 活跃状态和可见性是不同状态 |
| 暂停意味着整个程序停止 | 部分更新和 UI 输入可能继续运行 |
| 每帧恰好执行一次固定更新 | 可能执行零次、一次或多次 |
| 所有计时器都必须使用固定更新 | 普通计时器通常可累积 `delta` |
| 渲染阶段顺便修改游戏规则 | 更新状态与绘制呈现应分离 |
| 鼠标坐标可直接比较世界矩形 | 需要统一坐标空间 |
| `render_rect()` 就是物理位置 | 可能包含仅用于显示的插值偏移 |
| 离开场景就会重新初始化 | 场景可能缓存、复用或重置 |

## 11. 开发前检查清单

在新增对象或实现功能前，确认：

- 对象属于世界还是 UI？
- 哪个 `Scene` 或 UI 容器拥有它？
- 更新、输入或物理能力是否需要显式接入？
- 对应逻辑应该运行在普通更新、固定更新还是其他系统阶段？
- 对象何时销毁，实际由谁清理？
- 是否存在跨帧裸指针，或可能晚于对象执行的回调？
- 所有位置比较是否使用相同的坐标空间？

## 12. 总结

`Scene` 负责组织并持有对象；`GameObject` 和 `UiElement` 分别面向游戏世界与 UI。对象的更新、输入和物理能力应根据需求显式接入，不能只看继承关系。

场景或 UI 容器管理所拥有对象的生命周期；使用者仍须维护跨帧引用与回调的有效性。

普通更新和固定更新服务于不同的时间模型；渲染只应呈现状态，不应推进游戏规则。世界、屏幕与 UI 坐标需要明确区分；逻辑位置与插值后的显示位置也不应混用。
