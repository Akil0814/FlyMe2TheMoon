## 输入改造落地状态

本地输入已采用独立设备快照、`LocalPlayerRegistry`、`SceneInputRouter`、`ControllerService`／`ControllerManager`、`SceneControlContext`、通用 `ControlCommand` 与固定步消费，并迁移仓库内角色和示例。旧广播接口已移除，外部游戏需要迁移；引擎不要求单机建立网络会话。

本地游戏会话显式限定控制器生命周期，和网络会话是不同概念。控制器分场景／Session 作用域，跨场景保留实例时仍清空命令并解绑；普通场景不创建控制器上下文，`GameplayScene` 不自动创建控制器。游戏定义动作和具体映射，鼠标位移／滚轮使用按固定步一次消费的增量。

已确定的本地范围是共享 UI 单一操作权、显式设备绑定、屏蔽后释放／回中再恢复。双玩家示例采用共享相机；并未实现网络会话、网络身份、状态复制、预测、分屏或个人焦点树。

以下历史审计章节保留改造前背景，不应当作本次输入实现的 API 参考；迁移细节和验收入口见 Input 文档。

## 1. 背景、目标与范围

引擎后续计划通过 ENet 支持 Player Host 联机：一名玩家同时充当主机和本地玩家，其他玩家连接该主机。本文采用 Host 权威的设计方向，即 Host 负责决定游戏世界的最终状态，客户端提交操作并接收结果。

给 `GameObject` 增加唯一的 `uint64_t` ID 只能帮助识别对象，不能回答“谁可以控制它”“谁决定伤害”“客户端如何创建它”“输入在哪个时刻执行”等问题。不同机器各自递增生成 ID，也不能自动让同一个游戏实体获得相同身份。因此，联机准备工作必须覆盖身份、生命周期、输入归属、模拟时序及状态复制。

目标与目的如下：

| 目标 | 目的 |
| --- | --- |
| 单机与联机共用游戏命令执行入口 | 避免为本地玩家、Host 玩家和远端玩家维护不同玩法规则 |
| 将游戏输入从广播改为玩家到角色的路由 | 明确控制归属，支持切换角色及未来的本地多人 |
| UI 与游戏输入分流并协调 | 保持 UI 即时交互，避免打字、操作菜单时触发角色动作 |
| 游戏命令按固定模拟固定步消费 | 避免渲染帧率改变一次性动作的执行次数 |
| Host 统一决定权威状态 | 避免各端同时结算伤害、生成和销毁造成分歧 |
| 网络身份和网络会话为可选能力 | 单机无需创建连接，装饰、UI 等非复制对象无需承担同步职责 |
| 明确迁移边界 | 区分“不依赖网络运行”与“旧游戏完全不需要改代码” |

当前范围以 Player Host 基础联机为目标，不要求先拆分独立服务器程序，也不将主机迁移、客户端预测或回滚作为基础改造前置条件。中途加入、断线重连、公网连接方式等尚未确定，不能将本文理解为这些功能均已承诺实现。

ENet 位于传输层。游戏对象的身份对应、复制字段、控制权限、生成协议和玩法规则由引擎与游戏层定义，不会因为链接 ENet 而自动具备。

## 3. 统一输入架构

### 3.1 从对象广播转向玩家控制

改造前的游戏输入主路径可概括为：

```text
键盘／鼠标／手柄
    → InputSystem
    → InputActionMap
    → GameplayInputFrame／动作事件
    → 场景内游戏输入接收者
```

目标流程：

```text
键盘／鼠标／手柄
    → InputSystem
    → 输入路由与上下文
        ├→ UI 输入 → 焦点、按钮、菜单、文本框
        └→ 游戏动作映射 → 玩家控制器 → 玩家命令 → 角色
```

两条上层流程共用底层设备采集。UI 和游戏不应无条件同时响应所有输入；路由与上下文负责确定哪些输入能够进入哪条流程。

| 层次 | 目标职责 | 不应承担的职责 |
| --- | --- | --- |
| `InputSystem` | 采集设备状态和事件 | 直接决定哪个角色攻击或移动 |
| 输入路由与上下文 | 协调焦点、模态界面、设备及玩法输入屏蔽 | 执行伤害结算 |
| UI 输入 | 每帧处理焦点、点击、导航、文本及滚动 | 为普通 UI 交互生成网络角色命令 |
| 游戏动作映射 | 将设备输入解释为游戏动作 | 直接选择远端可控制的对象 |
| 玩家控制器 | 绑定控制目标，将动作转换为命令并提交 | 同时维护另一份权威玩法规则 |
| 命令队列与调度 | 缓存命令并在模拟边界交付 | 让网络回调直接修改正在遍历的世界 |
| 角色／玩法逻辑 | 根据命令执行移动、技能等行为 | 直接依赖键盘状态或 ENet 数据结构 |

玩家与被控制角色分离：玩家可以切换角色或载具，角色不需要知道命令来自本地设备、网络还是测试输入。该入口也为回放和本地多人提供基础，但不代表本次自动实现完整回放或多人设备分配系统。

### 3.2 命令与接口示意

以下是拟议设计示例，不是现有类型、最终公开签名或网络数据布局。具体玩法动作由游戏层定义，引擎只提供必要的路由、排队和模拟调度能力。

```cpp
// 游戏层示意：不是可直接序列化的内存布局。
struct ExamplePlayerCommand {
    std::uint64_t tick;
    std::uint32_t sequence;
    Vector2 move;
    std::uint32_t held_buttons;
    std::uint32_t pressed_buttons;
};

// 拟议调用关系，接口名称和句柄类型尚未定稿。
controller.possess(character_handle);
character.apply_command(command);
```

`tick` 用于表达命令与模拟时刻的关系，`sequence` 可用于排序和去重。客户端固定步如何映射到 Host 固定步、如何处理迟到命令，以及序号回绕规则需要在协议设计阶段确定；客户端提供的数值不是可信的权威时钟。

移动、跳跃等字段仅用于说明。引擎不能把所有游戏的攻击、技能、交互等固定成一份不可扩展的基础协议。按钮位图只适合表达可合并的状态或动作；需要保留多次快速操作时，应使用事件队列或计数。

### 3.3 每帧采样与固定步消费

UI 通常每帧响应，游戏输入每帧采集后进入缓存，由固定模拟固定步消费。一帧可能执行零次、一次或多次模拟，输入语义必须在这些情况下保持一致。

| 情况 | 目标行为 |
| --- | --- |
| 移动、持续防御等保持输入 | 作为持续状态供模拟使用，直到释放或被上下文清理 |
| 一次跳跃或攻击按下 | 作为一次性动作，仅消费一次 |
| 本帧没有模拟固定步 | 保留待消费动作，不能在帧末直接清空 |
| 本帧补跑多个固定步 | 不得将同一次按下复制执行多次 |
| 消费前发生多次有效操作 | 对要求保留次数和顺序的动作使用队列或计数 |
| 网络重复提交同一动作 | 通过命令身份和消费记录避免重复执行；不能仅依赖按钮状态 |

持续状态与动作事件在语义上分开，即使未来协议将它们打包在同一消息中，也不能混淆其消费方式。

### 3.4 UI 与游戏输入的协调

| 输入上下文 | UI 行为 | 游戏行为 |
| --- | --- | --- |
| 正常游戏 | HUD 等界面可按规则接收指针输入 | 玩家控制器接收允许的游戏动作 |
| 暂停菜单或模态窗口 | 接收导航、确认和取消 | 屏蔽相关角色操作；联机世界是否暂停另行决定 |
| 聊天框获得焦点 | 接收文本和编辑操作 | 键盘不再同时触发移动和攻击；其他设备按上下文规则处理 |
| 窗口失焦或控制目标切换 | 更新焦点与交互状态 | 清理或终止旧目标的持续输入和待执行动作，避免残留操作 |

屏蔽游戏输入不能只停止产生新命令，还必须让已经生效的持续移动等状态结束。上下文切换不应在恢复后突然执行菜单期间积累的攻击，也不能把旧角色的命令交给新角色。

普通 UI 悬停、菜单焦点不需要网络同步。开始游戏、请求全员暂停等影响世界的 UI 操作，可以转换为显式会话请求或游戏命令，由 Host 处理。

具体的按设备屏蔽、事件消费优先级和恢复按键策略需在输入接口设计时确定；上述表格规定应达到的行为，不声明当前路由已经实现这些规则。

## 4. 单机与 Player Host 运行流程

### 4.1 三种命令来源，共用执行逻辑

```text
单机：
本地控制器 → 命令队列 → 本地世界执行 → 本地展示

Host 本地玩家：
本地控制器 ─────────────────┐
                           ↓
                       权威命令队列 → Host 世界模拟
                           ↑              ├→ Host 本地展示
远端控制器 → ENet → Host 校验 ┘              └→ 状态快照 → 客户端应用与展示
```

Host 本地命令直接入队，无需经网络绕行，但与远端命令共用玩法处理入口。角色移动和攻击不应同时在本地输入回调与权威模拟阶段执行。

Host 只需要一份权威世界，并直接渲染该世界。无需为了模拟服务器和客户端再运行两份相同场景，否则容易出现重复物理、伤害或生成。

客户端角色副本需要明确模拟职责：哪些只展示权威结果，哪些未来参与预测。没有预测设计时，不应无条件让副本执行权威 AI、伤害、掉落和生成逻辑。未来预测仍需与权威校验及结果修正配套。

### 4.2 玩家身份与权限

Host 根据连接识别玩家，再根据玩家与角色的绑定关系路由命令。不能直接相信客户端声称的玩家身份或控制目标。

拥有角色意味着有权提交该角色的操作请求，不意味着可以直接决定生命值、命中结果、掉落或其他玩家的状态。命令解码和参数校验属于网络入口，合法玩法状态判断属于权威游戏逻辑。

### 4.3 暂停、菜单与离开

单机继续允许暂停本地世界。联机应分开“打开本地菜单”“停止本地角色输入”“暂停全体世界”三个概念。

建议默认行为是 Host 打开菜单后，权威世界与网络轮询继续运行，只屏蔽该玩家相应输入。若游戏需要全员暂停，应由 Host 明确同步暂停状态，网络服务仍保持工作。

Host 退出后关闭会话是基础版本的建议默认值，可省去主机迁移和权威交接；该策略尚未作为最终产品要求确认。客户端退出时，需要清理玩家绑定与相关网络状态，其角色销毁或保留方式由游戏规则决定。

## 5. 网络身份、生命周期与状态同步

### 5.1 区分身份的作用域

下列名称均为拟议概念，除现有 `PhysicsObjectHandle` 外，不表示已存在对应 API。

| 身份 | 用途 | 分配与边界 |
| --- | --- | --- |
| ObjectId | 识别本进程中的对象 | 本地生成，不要求各机器相同 |
| NetworkId | 对应各端的同一个网络实体 | Host 分配，客户端沿用 |
| PlayerId／OwnerId | 识别玩家及控制归属 | 与对象身份分开，绑定由 Host 管理 |
| `PhysicsObjectHandle` | 引用本地物理对象 | 保留现有物理系统职责，不作为网络身份 |

网络 ID 可以使用 `uint64_t`，但其唯一性范围和复用规则比位数更重要。建议会话内不复用网络 ID，并通过会话／世界代次区分重开房间或切换世界后的消息。旧会话消息不得修改新对象。

网络身份应为可选能力。可通过组件、接口或外部注册表实现，具体形式待定；UI、装饰或本地特效无需自动进入复制系统。

### 5.2 注册、生成与销毁

目标生命周期包含：

1. Host 决定生成，分配网络身份并确定类型标识与初始状态。
2. 客户端通过稳定的 `TypeId/PrefabId` 等拟议标识调用工厂创建对应对象，不传递 C++ 指针或依赖各端构造顺序。
3. 将网络身份登记到查找表，拒绝重复身份，完成后方可应用后续状态。
4. Host 决定销毁并发送生命周期消息；对象释放前清理查找表、控制绑定及其他外部引用。
5. 场景整体退出、重置和会话断开也必须覆盖注销流程，不能只依赖逐对象正常销毁。

注册表可提供 `NetworkId → GameObject` 映射，但其引用必须受生命周期约束。已标记销毁的对象不应继续接受有效玩法命令，即使内存尚未释放。

网络收包先解码、校验和排队，再在安全更新边界创建、修改或销毁对象。当前对象添加会修改对象容器和接口列表，在遍历期间直接执行生成可能使迭代器失效；未来即使增加收包线程，也不能让该线程直接修改场景。

全量初始状态是客户端进入世界的基础。中途加入还需要把全量状态与后续增量衔接起来，该能力尚未确定是否进入首版。

### 5.3 统一模拟时序

目标概念顺序为：

```text
轮询网络并缓存消息／采集本地输入
    → 安全边界应用生命周期变更
    → 固定 tick：应用命令 → 游戏逻辑 → 物理 → 完成本 tick 状态
    → 按发送节奏生成快照
    → 渲染插值与 UI 展示
```

固定模拟必须覆盖无刚体的权威逻辑，不能仅由物理对象获得固定步。Gameplay 与物理应共用时间基准，避免分别累计时间、各自补步造成错位，也要避免旧物理固定回调与新场景固定更新重复调用同一逻辑。

模拟固定步、渲染帧率和快照发送频率不是同一概念。快照可以低于模拟频率发送。具体频率、补步上限、过载策略和迟到命令处理需要后续明确；现有物理补步限制不能未经评估就被当作完整网络时钟策略。

### 5.4 同步字段与物理校正

同步应使用明确的状态字段，例如位置、速度、生命值和动作状态。不能直接发送 `GameObject` 或 C++ 结构体的原始内存；实际协议还需定义字段编码、长度、版本和校验规则。

物理对象应用权威校正时，应通过现有 [PhysicsWorld 接口](../../../engine/physics/physics_world.h)中的 `set_transform()` 等入口，使刚体和游戏对象保持一致，速度是否保留或替换也必须符合收到的状态。单独修改 `GameObject` 位置不足以完成物理校正。

客户端插值用于平滑展示，不能把渲染位置当作权威碰撞位置。现有物理插值与网络快照插值必须有明确组合或择一规则，不能让两者独立覆盖同一偏移并重复平滑。该规则与远端对象是否参与客户端物理相关，需要在同步实现阶段确定。

### 5.5 会话模块与消息传输

拟议的独立 `NetworkSession` 模块封装 ENet 初始化、连接、收发、断线、消息解码及必要统计，将 ENet 类型限制在网络边界。单机不创建网络会话，不应为了消费本地命令而建立回环连接。

建议区分消息用途：

| 消息用途 | 建议策略与约束 |
| --- | --- |
| 生成、销毁及关键会话控制 | 可靠传输，并处理重复或失效生命周期消息 |
| 连续状态快照 | 可使用不可靠有序传输，以较新有效状态替换旧状态 |
| 玩家命令 | 按持续状态与一次性动作语义设计重发／冗余及去重，不能因丢包永久丢失关键动作 |

关键消息与连续快照建议分通道，避免不必要的相互等待。不同通道不保证全局业务顺序，因此必须处理“快照先于生成到达”：采用有界缓存、忽略并等待后续完整状态或其他显式策略，具体选择待协议设计确定。销毁后的迟到状态不得使对象复活。

解码入口需要验证消息类型、版本、长度、字段范围、会话归属和操作权限。ENet 的连接与传输能力不等于已经解决公网可达性、房间发现、NAT 穿透或中继，这些是另外的产品与部署决策。

## 6. 兼容性、迁移与实施顺序

### 6.1 讨论方向的演进

最初讨论的是低侵入准备方案：保留现有单机输入路径，通过可选联网场景或运行时增加玩家路由和网络行为。这种方案可以减少旧游戏修改。

后续重点转向统一改造游戏输入：单机与联机均通过玩家控制器和命令执行玩法。该方向更有利于保持规则一致，但会产生一次性迁移成本，不能同时承诺所有旧游戏零修改。

两项兼容性目标必须分开：

- **单机不依赖网络：** 迁移后的游戏无需网络会话即可运行，UI 也不需要通过网络处理。
- **旧代码源兼容：** 取决于是否保留旧接收器及适配层，尚未确定过渡周期，不能无条件保证。

给已有单机游戏增加联机，还需要游戏层定义权威逻辑和同步字段；统一命令入口只是基础，不会自动将所有游戏变成联机游戏。

### 6.2 游戏层迁移影响

| 旧模式 | 目标模式 |
| --- | --- |
| 角色实现游戏输入接收器并接收广播 | 玩家控制器绑定角色，角色消费命令 |
| 输入回调直接移动、施力或攻击 | 回调生成／缓存输入意图，在模拟固定步执行 |
| 角色读取全局键盘状态 | 角色读取传入命令 |
| 角色都收到同一份输入 | 每个玩家只控制其绑定对象 |
| 各处自行结算玩法状态 | 区分权威逻辑与客户端展示逻辑 |

保留旧接收器作为过渡路径是可选方案，不是已经确定的永久架构。同一角色不得同时消费旧输入和新命令，适配器也不能在两个入口重复触发一次攻击。正式改造时必须明确过渡、示例迁移与旧接口移除安排。

### 6.3 建议实施路线

| 阶段 | 主要交付 | 阶段目的 |
| --- | --- | --- |
| 1 | 玩家控制器、命令入口、UI／游戏上下文协调 | 先明确输入归属和屏蔽行为 |
| 2 | 固定步消费规则与现有示例迁移 | 在纯单机条件下验证命令不丢失、不重复 |
| 3 | 对象身份、查找、注册与移除通知 | 建立跨系统安全引用和网络对象生命周期基础 |
| 4 | ENet 会话、Host 身份校验与远端命令传输 | 让本地和远端命令进入同一权威路径 |
| 5 | 网络生成销毁、状态快照与客户端插值 | 形成可观察的基础联机闭环 |
| 6 | 按需求增加中途加入、重连和预测 | 在基础行为稳定后扩展体验 |

上述为建议路线，不代表本文编写任务已授权实施这些代码改造。每个阶段需要先解决影响该阶段的待定接口与策略，再进入实现。

## 7. 后续实现的验收场景

这些是未来代码改造的验收目标，不是本次已运行或通过的测试。

| 场景 | 预期结果 |
| --- | --- |
| 不创建网络会话运行单机 | 输入、玩法、UI 和暂停正常工作 |
| 两个玩家分别提交移动命令 | 每份命令只作用于其绑定角色 |
| 按下攻击后本渲染帧没有模拟固定步 | 动作保留到可消费的固定步 |
| 一帧补跑多个模拟固定步 | 同一次按下只执行一次 |
| 快速提交多个不可合并动作 | 按所定义的次数和顺序消费，不被布尔值覆盖 |
| 打开聊天框、菜单或切换控制目标 | 不误触玩法，无残留移动，不向新目标投递旧动作 |
| Host 本地玩家攻击 | 仅在权威入口结算一次，无本地与服务器双重执行 |
| 远端伪造其他玩家或对象的操作 | Host 拒绝越权命令 |
| 重复或乱序命令、丢失快照 | 不重复结算一次性动作，不回退到过期状态 |
| 生成、状态和销毁消息交错到达 | 不访问未知对象，不让迟到状态复活已销毁对象 |
| 对象释放、切场景和断线 | 无悬空映射，旧会话／世界消息不影响新对象 |
| 对物理角色应用权威校正 | 下一物理步不会恢复为未校正的旧刚体位置 |
| 客户端同时存在物理与网络插值 | 逻辑状态与显示位置职责清晰，无重复平滑覆盖 |
| Host 打开本地菜单 | 网络轮询持续，连接不因本地菜单停摆 |

## 8. 待定事项与建议默认值

以下事项不能仅凭本文直接实施为既定产品规则。

| 待定事项 | 当前建议或约束 |
| --- | --- |
| 旧输入接口过渡周期 | 可保留临时适配，但不得双重消费；保留多久及何时移除未定 |
| 最终公开 API 与扩展方式 | 本文控制器、命令及方法名为示意，需要落实游戏层扩展与引擎边界 |
| 网络身份的承载方式 | 组件、接口或外部注册表待选；必须保持可选能力 |
| 玩家设备分配与上下文优先级 | 明确玩家到角色路由；本地多人设备管理与具体消费优先级未定 |
| 模拟与快照频率 | 共用模拟时基，发送频率可独立；具体数值未定 |
| 输入时钟与传输策略 | 明确固定步映射、迟到处理、一次性动作重传与去重规则 |
| 网络插值与物理角色策略 | 选择远端展示和物理参与方式，避免插值互相覆盖 |
| 中途加入 | 未确定是否首版支持；若不支持，需显式禁止开局后加入 |
| 断线重连 | 身份恢复、角色保留和全量重同步策略未定 |
| 客户端预测与回滚 | 可后续增加，不是基础改造前置要求 |
| Host 退出策略 | 建议首版结束会话；主机迁移不作为前置要求，最终体验待确认 |
| 联机全员暂停 | 建议本地菜单不暂停世界；若支持全员暂停，由 Host 明确同步 |
| 公网连接与 NAT 穿透 | 房间发现、直连、穿透或中继方案另行确定，不能从 ENet 依赖推导已支持 |

后续实现应先冻结相关阶段的接口与行为，再将已实现部分更新到对应子系统文档。本文保留为目标设计依据，不能用未落地的示意 API 替代源码参考。
