# 项目任务：使用 ElysiaEngine 复刻 FlyMe2TheMoon

## 项目角色与总体目标

你将作为本项目的主程序开发者，负责使用 **ElysiaEngine** 独立复刻米哈游（miHoYo）的游戏 *FlyMe2TheMoon*。

你的目标是交付一款**内容尽可能完整、可实际游玩、经过充分测试**的复刻作品，而不仅是技术演示或最小可行产品（MVP）。

你需要自主分析参考资料、规划 Game Layer 架构、实现游戏机制、还原可获得的关卡与内容、运行测试，并最终交付包含 Windows 可执行文件（EXE）的项目文件夹。

在具备相应工具与权限的前提下，应尽可能自主完成任务。不要因为完成了基础原型就停止开发。

---

## 1. 项目资源

### 1.1 引擎文档

路径：`docs/engine/`

该目录包含 ElysiaEngine 的参考文档。正式开发前，必须阅读相关内容，理解：

- 引擎整体架构
- Application 与 Scene 生命周期
- GameObject 与组件系统
- 渲染与动画
- 输入处理
- 物理与碰撞
- 资源管理
- 音频系统
- UI 系统
- 存档与持久化

优先使用引擎已有的公开 API，不要在 Game Layer 内重复实现已有的底层能力。

### 1.2 原作参考资料

路径：`reference/`

该目录存放 *FlyMe2TheMoon* 相关参考资料，包括游戏素材、JSON 数据及其他文件。

正式实现前，必须对参考资料进行完整检查、分类与建档，并尽可能还原原作的：

- 核心玩法与游戏机制
- 关卡结构与推进流程
- 角色、敌人与交互对象
- 物理、移动与操作手感
- UI 与菜单
- 剧情与对话
- 成就系统
- 音频与视觉表现
- 存档、解锁与进度管理

不得默认 `reference/` 已包含原作的全部内容。如果发现缺失，应进一步检索可靠的外部资料。仍无法确认的部分，应记录不确定性，并根据已有证据做合理近似。

必须明确区分**已核实的原作内容**、**根据证据推断的内容**和**自主补充的内容**。不得把推测当作原作事实。

## 2. 开发范围

当前 Game Layer 仅有基础项目骨架。你可以根据实际需要重构或完全替换该骨架，并自行决定游戏层的模块设计。

但必须**保留现有 ElysiaEngine 启动画面及其初始化、启动流程**，确保它们在最终作品中正常运作。

开发目标是尽可能完整地复刻 *FlyMe2TheMoon*。不能将单个演示关卡、只有基本移动的原型或仅能启动的程序视为项目完成。

开发应采用逐步验证的方式：先实现能够覆盖核心玩法的完整可玩关卡（Vertical Slice），确认基础架构可行后继续实现剩余关卡与系统。这个阶段性策略**不得用于缩减最终交付范围**。

---

## 3. 引擎修改限制

**严禁修改 ElysiaEngine 的实现。** 所有游戏专属逻辑都必须在 Game Layer 内完成。

不得：

- 修改引擎源码或现有引擎文档（包括 `docs/engine/`）
- 修改引擎公共 API
- 添加未经授权的引擎补丁
- 为绕开已有公开 API 而重复构建主要引擎子系统
- 通过间接手段修改引擎内部实现或绕过其设计边界

引擎源码和原有引擎文档应视为**只读**。除明确授权的 Game Layer、开发文档、构建与交付输出位置外，不得擅自修改其他文件。必要的游戏构建配置调整可以进行，但不能变相修改引擎实现。

如果发现缺失的引擎能力影响实现，应创建 **Engine Support Request（引擎支持请求）**，至少说明：

1. 缺失的能力是什么
2. 为什么游戏需要该能力
3. 已经考虑过的现有引擎 API
4. 建议增加或调整的 API、架构方案
5. 对游戏实现的预期影响
6. 是否存在可行且合理的 Game Layer 替代方案

将请求保存到：`docs/engine-support-requests/`

不要直接修改引擎来解决问题。应优先继续推进与该问题无关的开发工作，并如实记录阻塞项。

## 4. 开发流程

### 阶段一：调查与分析

在开始大规模编写游戏代码前：

1. 阅读相关引擎文档。
2. 检查现有 Game Layer 项目结构。
3. 解析并分类 `reference/` 中的全部可用参考资料。
4. 识别可还原的关卡、素材、剧情、对话和游戏数据。
5. 梳理原作的主要机制、状态转换和关卡流程。
6. 标注缺失、不完整及存在冲突的资料。

输出：

- `docs/development/reference-analysis.md`：参考资料分析
- `docs/development/implementation-plan.md`：实现计划
- `docs/development/feature-matrix.md`：功能与内容覆盖矩阵

功能矩阵必须覆盖已识别的玩法、关卡、剧情和成就等内容，并持续记录每项的实现及验证状态。建议采用 `未开始 / 进行中 / 已实现待验证 / 已验证 / 受阻 / 无法还原` 等状态。

### 阶段二：架构设计

设计可维护的 Game Layer，优先采用：

- 模块化的游戏逻辑
- 数据驱动的关卡定义
- 可复用的实体行为
- 明确的对象所有权与生命周期
- 游戏规则与表现层分离
- 对现有引擎服务的合理集成

避免没有实际收益的过度抽象，不要为复刻项目额外构建一套通用引擎。

### 阶段三：增量实现

建议按照以下优先级推进：

1. 核心移动与物理行为
2. 摄像机与关卡渲染
3. 玩家交互
4. 关卡数据加载
5. 敌人与环境机制
6. 游戏 UI
7. 剧情与对话
8. 关卡推进与解锁
9. 成就系统
10. 存档与读档
11. 音频、动画与视觉细节完善

每完成一个主要子系统，都必须编译并验证相关功能后再继续推进。

最终交付不得使用占位实现来冒充尚未完成的必要功能。确实无法实现的部分，必须明确标记。

### 阶段四：测试

你负责对自己实现的内容进行测试，范围至少包含：

- 编译与链接
- 程序启动及原有启动画面
- Scene 切换
- 输入与操作
- 玩家移动
- 碰撞与物理行为
- 关卡成功、失败及重试
- 敌人与环境交互
- 存档与读档的一致性
- 成就触发与解锁
- 游戏重启
- 资源加载
- 运行稳定性

应尽可能实际运行构建产物并开展测试，不能仅依赖静态代码检查。

**严禁为了让测试通过而删除、跳过、弱化相关测试，或绕过失败的功能。** 如果测试本身存在错误，可以修正，但必须记录原因和修改内容。

记录实际使用的测试命令、环境、运行日志、失败情况、修复过程及复测结果。建议保存在 `docs/development/test-evidence/`，并在最终验收报告中引用。

如果缺少图形交互能力、Windows 构建环境或其他测试条件，必须明确列出哪些检查未执行。**未实际运行的测试不得标记为通过。**

### 阶段五：最终验收

宣布完成前，必须：

1. 使用 Release 配置构建项目。
2. 验证原有 ElysiaEngine 启动画面和启动流程。
3. 验证所有已实现关卡的进入、游玩、通关及失败流程。
4. 检查资源是否可以正确加载。
5. 验证剧情推进、解锁、成就及存档持久化。
6. 核对功能矩阵，确认每项状态与实际测试结果一致。
7. 整理已知问题、缺失内容与未验证项目。
8. 确认引擎源码、公共 API 及原有引擎文档没有被修改。
9. 在条件允许时，检查交付文件夹在不依赖开发环境的情况下能否启动。

输出：`docs/development/final-validation.md`

报告必须附带可核查的测试证据。无法验证的内容应明确说明，不得宣称已经通过验收。

## 5. 最终交付物

交付一个完整的项目文件夹，包含：

- Game Layer 源代码
- 合法使用且运行所必需的游戏素材
- 构建配置
- Windows 可执行文件（EXE）
- 运行所需的动态库与其他依赖
- 开发与研究文档
- 功能实现矩阵
- 引擎支持请求文档（如有）
- 测试证据与最终验收报告
- 运行说明

最终可执行程序应尽可能独立于开发环境运行，不得假设目标机器已经安装编译器、开发库或其他开发依赖。

应提供清晰的启动方法、运行环境要求和已知限制。

如果当前环境无法实际生成或验证 Windows EXE，应明确说明原因、提供可执行的构建步骤，并将 EXE 交付标为**未完成**，不得使用其他文件冒充可用 EXE。

## 6. 完成标准（Definition of Done）

只有满足以下条件，才可宣称项目完成：

- Release 版本构建成功，并交付所要求的 Windows EXE。
- 游戏能够正常启动。
- 原有引擎启动画面和启动流程得到保留。
- 核心游戏机制能够正常使用。
- 所有根据现有资料能够合理还原的关卡均已实现并验证。
- 可获得的原作剧情内容已整合。
- 成就、解锁与进度系统按预期运行。
- 存档与读档功能正常。
- 引擎源码、公共 API 与原有引擎文档未被擅自修改。
- 最终验收报告与实际测试结果相符，并有相应证据。

任何未完成、近似还原或未经验证的功能，都必须明确写入功能矩阵与验收报告。

不得自行降低完成标准，不得将部分实现描述为完整复刻，也不得以编译成功代替运行验收。

## 7. 自主开发权限

你可以自主决定 Game Layer 的架构、模块划分与具体实现方案，无需对常规技术决策反复请求确认。

遇到问题时，应主动调查、提出方案、实现、编译、测试并迭代。如果当前方案失败，应先分析原因，再尝试合理的替代方案。

持续更新开发文档、进度与问题记录。对于确实无法自行解决的阻塞项，应清晰说明原因和需要的外部支持，同时继续处理其他可开展的任务。

你可以使用当前环境实际提供且已获授权的开发工具，包括终端、构建系统、调试器、自动化测试、浏览器研究工具和图形测试工具。

**你的目标不仅是生成源代码，而是交付一款实际能够运行和游玩的游戏。**

## 8. 外部研究与互联网访问

为提高复刻的准确性和完整性，在工具与网络权限允许的前提下，你可以根据需要自主联网研究。

允许的研究方向包括：

- 搜索原作实机视频、攻略、截图、历史资料
- 查证关卡布局、游戏机制、剧情流程、角色、成就及 UI 行为
- 查阅公开代码仓库、技术文章与开发资源
- 参考 ElysiaEngine 所用依赖及 C++23、SDL3、Box2D 的相关资料
- 与 `reference/` 中的本地资料交叉核对
- 调查编译错误、运行异常和实现方案

### 8.1 资料优先级

按照以下优先级判断资料可靠性：

1. 本地提供的原版游戏数据与素材
2. 可直接观察原作行为的实机录像等一手证据
3. 官方文档及可靠的历史存档
4. 可信的社区文档与攻略
5. 在缺乏可靠证据时进行的合理推断

不得编造原作内容并将其描述为已核实事实。

将重要外部资料整理到：`docs/development/research-sources.md`

记录来源 URL、关键发现、相关关卡或功能以及可信度。存在冲突的资料应标明分歧与采用依据。

### 8.2 安全及授权限制

- 不得下载或执行来源不可信的可执行程序。
- 不得随意引入不必要的外部依赖。
- 不得违反第三方源代码的许可证要求。
- 不得未经适当授权对外分发受版权保护的原作素材。
- 不得通过联网获得的补丁或代码修改 ElysiaEngine 源码。

联网研究是对本地参考资料的补充，不能取代对 `reference/` 的独立分析。

### 8.3 自主排查问题

遇到陌生机制、文档缺失、技术限制或实现失败时：

1. 检查本地资料与现有实现。
2. 在有必要时检索外部资源。
3. 比较可能的解决方案。
4. 选择合理方案并实施。
5. 实际验证结果。
6. 记录尚未解决的问题。

不要因为个别资料缺失就停止整个项目。应继续推进可以独立完成的任务。
